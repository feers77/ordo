ERP/CRM API-first · sin frontend

ORDO ERP

Un ERP/CRM completo cuyo consumidor primario es un agente de IA, no un humano frente a una pantalla. No hay interfaz gráfica: hay contrato, introspección en runtime, idempotencia, simulación y capacidades delegadas con límites.

Python 3.12 · FastAPI · PostgreSQL 17 F1 IAM implementada F2 Kernel funcional F4 Contabilidad + e-invoicing F5 Ventas y compras F3 Servidor MCP AGPLv3

Contabilidad y localizaciones

El módulo account implementa contabilidad por partida doble. Los invariantes están escritos como property-based testing porque un error contable no falla ruidosamente: aparece en el cierre, cuando ya es caro de arreglar.

  • Un asiento cuadra o no se contabiliza. No existe el estado «asiento descuadrado guardado».
  • Una partida nunca tiene debe y haber a la vez, y ningún importe es negativo.
  • Un asiento contabilizado no se modifica ni se borra: se emite su reversión, y el original permanece. Un test verifica que el efecto neto de las dos piezas es exactamente cero.
  • El número legal se toma al contabilizar, no al crear el borrador, así que un borrador descartado no deja un hueco en la numeración.
  • Contabilizar en un período cerrado devuelve ACCOUNT_PERIOD_LOCKED.

Motor de impuestos

Precio con impuesto incluido o excluido, retenciones que no suman al total, impuestos compuestos que declaran explícitamente sobre qué base gravan, y redondeo por línea o por documento como decisión declarada: ambos criterios existen en la práctica y difieren en céntimos, así que se elige en vez de imponer uno en silencio.

Todos los importes son Decimal o string decimal. Pasar un float es un error explícito.

Localizaciones: Chile y Paraguay

Ambos packs están en estado draft. Contienen lo que se puede afirmar citando la norma —tasa general de IVA, códigos de documento electrónico, algoritmo del dígito verificador del identificador tributario—, pero el plan de cuentas, los impuestos específicos y las retenciones requieren revisión de un contador de cada país antes de usarse para declarar impuestos. Cada manifiesto lista qué falta.

El framework rechaza cargar un pack que no cite sus fuentes normativas: un dato fiscal sin norma detrás no se puede verificar ni defender ante una fiscalización.

Facturación electrónica: SII y SIFEN

El módulo einvoicing modela el documento electrónico como una máquina de estados explícita: draft → generated → signed → sent → accepted/rejected, con contingency para cuando la autoridad no responde. Cada transición es un método; una transición inválida es EDI_INVALID_TRANSITION. Los rangos de numeración autorizados —el CAF chileno y el timbrado paraguayo son el mismo concepto— asignan folios que no se reciclan: un folio quemado queda quemado.

  • Chile (SII): lectura del CAF, timbre TED firmado de verdad (RSA-SHA1 con la clave del CAF, como exige el formato), DTE 33/34/39/52/56/61 con referencia obligatoria en notas de crédito y débito, sobre EnvioDTE y lectura de acuses (TrackID, EPR/RCT). Un DTE aceptado no se anula: se corrige con NC.
  • Paraguay (SIFEN): CDC de 44 dígitos con dígito verificador módulo 11, XML del DE con subtotales por tasa (10 %, 5 %, exento), URL del QR firmada con el CSC, y respuestas 0260/0300/1xxx. El SIFEN sí permite anular un DE aprobado dentro del plazo.

La firma XMLDSig del documento completo está implementada (ADR-014 aceptado: firma enveloped con signxml, RSA-SHA256 por defecto y RSA-SHA1 solo donde el formato del SII lo exige; la verificación detecta manipulación y certificado incorrecto). El envío productivo requiere certificados reales en el vault y el ambiente de certificación de cada autoridad.

Ventas y compras con asiento automático

Las órdenes de venta y compra (sale.order, purchase.order) cierran el ciclo comercial: confirmar fija los totales con el motor de impuestos y toma número de secuencia; facturar construye el asiento —cliente al debe; ingreso e IVA al haber; retenciones en su propia cuenta reduciendo la contrapartida— y lo contabiliza en la misma operación. No existe el estado «facturada pero sin asiento». El constructor de partidas está probado con Hypothesis: cualquier combinación de líneas, descuentos y retenciones cuadra o falla con un código estable.

Qué es ORDO #

ORDO es un ERP/CRM solo backend. Cobertura funcional de un ERP completo —ventas, compras, inventario, contabilidad, manufactura, proyectos, RRHH— más un framework declarativo de localizaciones fiscales cuya primera ola es Chile.

La diferencia no es que le falte la pantalla. La diferencia es que todo el contrato está diseñado para que quien lo opere sea un programa que razona, se equivoca de formas creativas y reintenta. Eso cambia requisitos de fondo: descubrimiento por introspección en vez de manual de usuario, errores con código estable en vez de mensajes para humanos, idempotencia obligatoria en vez de "no aprietes dos veces".

Regla de oro del proyecto

Si un agente puede dejar la contabilidad en un estado inconsistente, el bug es del sistema, no del agente.

Corolario operativo: no se escribe frontend, nunca. Si una tarea parece requerir interfaz, el entregable es un endpoint más el schema que permite a un cliente construir esa interfaz por su cuenta.

Por qué existe #

Un ERP tradicional expuesto por API sigue siendo un CRUD sobre un ORM: asume que al otro lado hay una persona que lee el formulario, entiende el mensaje de error y sabe que no debe apretar "Guardar" dos veces. Ninguna de esas tres cosas es cierta cuando el operador es un agente.

Arquitectura de servicios #

Siete servicios, todos stateless salvo la infraestructura con estado (PostgreSQL, Redis, NATS, MinIO). La identidad vive en un PostgreSQL separado del de los tenants: comprometer datos de negocio no entrega el directorio de principals.

El kernel (packages/ordo-core) es una librería, no un servicio: no depende de HTTP. La cola de trabajos y el outbox viven en tablas de PostgreSQL precisamente para que encolar un trabajo o emitir un evento ocurra dentro de la misma transacción del cambio de negocio. Si el commit falla, el trabajo nunca existió.

La API #

Toda la superficie implementada hoy la sirven dos procesos: ordo-api y ordo-iam. Los ejemplos de esta sección salen de los tests de integración y end-to-end del repositorio (tests/integration/api/test_records_api.py, tests/e2e/test_f1_flow.py, tests/e2e/test_f2_kernel_flow.py).

Registros — /api/v1/{model} #

Una sola familia de endpoints sirve a todos los modelos del registry. {model} es el nombre técnico del modelo (res.partner, sale.order). Un modelo que no está registrado devuelve MODEL_NOT_FOUND (404), nunca un error genérico.

GET/api/v1/{model}search_read

Busca y lee en una sola llamada. Parámetros: domain (JSON), fields (lista separada por comas), limit (por defecto 80, máximo 500), cursor, order.

Request
GET /api/v1/res.partner?domain=[["name","=","Alfa"]]&fields=name&limit=80
X-Ordo-Tenant: apitest
200 OK
{
  "rows": [ { "id": 1, "name": "Alfa" } ],
  "next_cursor": null
}

next_cursor es null cuando no hay más páginas; si lo hay, es un cursor opaco (base64 del último id) que se pasa en la llamada siguiente. El campo id se incluye siempre, aunque no lo pidas en fields. Nota de fidelidad: el parámetro order está en el contrato, pero el orden efectivo hoy es id asc, que es lo que hace estable la paginación por cursor.

Introspección — /meta/v1/* #

Aquí es donde un agente deja de necesitar documentación. El schema semántico se genera desde el registry, nunca se escribe a mano: si un campo de negocio no declara agent_hint, el registry se niega a construirse y el servicio no arranca. En consecuencia, el schema que lee un agente siempre está completo.

GET/meta/v1/schema?models=… &format=llm|full

format=llm (por defecto) omite los campos de auditoría (create_uid, create_date, write_uid, write_date, version); format=full los incluye. id siempre aparece, y company_id tampoco se omite aunque lo gestione el kernel: a qué compañía pertenece un registro es información de negocio que el agente necesita para operar en un tenant multi-compañía. models filtra por nombre; sin él, devuelve todo el registry.

Lenguaje de dominios

Los filtros usan una sintaxis prefija con tuplas, ampliamente conocida por los modelos de lenguaje, de modo que un agente puede escribirlos sin entrenamiento específico: 

[("state", "=", "sale"),
 "|", ("partner_id.country_id.code", "=", "CL"),
      ("amount_total", ">", 1000000)]

El & es implícito entre términos; | y ! son explícitos. Las rutas punteadas sobre Many2one generan JOINs (máximo 4 saltos). El compilador no interpola nunca: todo valor viaja como parámetro vinculado, y todo identificador se valida contra el registry antes de tocar el SQL. Un campo inexistente es DOMAIN_UNKNOWN_FIELD, no texto que llegue a la base.

Identidad y autorización — /iam/v1/* #

ordo-iam no es un OpenID Provider: la autenticación humana la hace un OP externo (Keycloak en las fases actuales) detrás de una interfaz OIDC genérica. ordo-iam aporta lo que un OP estándar no da: el agente como principal de primera clase, con dueño, capacidades delegadas, límites y presupuesto.

GET/iam/v1/mebearer de usuario

Verifica el token del OP y resuelve la identidad contra el directorio del tenant. Nunca auto-crea usuarios: el primer login solo vincula un usuario ya aprovisionado, del mismo tenant y con email verificado. Una identidad desconocida es IAM_UNKNOWN_IDENTITY (401) aunque el OP la haya autenticado correctamente.

  "tenant": "acme",
  "type": "user",

  "email": "persona@acme.cl"

Registra un agente. Quien llama queda como owner. El secreto se entrega una sola vez: es aleatorio de 32 bytes, no una contraseña, y en la base solo queda su hash salteado.

POST/iam/v1/tokenRFC 8693 · form-urlencoded

Token exchange: el agente presenta sus credenciales y el token del usuario delegante, y recibe un access token propio con la cadena de delegación en el claim act. Sin grants vigentes no hay token: IAM_NO_CAPABILITIES (403).

Convenciones no negociables #

Estas reglas forman parte del contrato desde v1. No son estilo: son las garantías sobre las que un agente puede construir un plan de varios pasos sin verificar cada supuesto.

Dinero como string decimal

Nunca float, en ninguna capa: Decimal en Python, NUMERIC en PostgreSQL, string decimal en JSON. El tipo Monetary rechaza un float tanto en la definición del campo como en la escritura. Los acumulados diarios de los límites se llevan en enteros de micros.

Timestamps UTC ISO-8601

Todo instante es tz-aware y viaja en UTC. La zona de presentación la define el tenant; el contrato no negocia con horas locales.

Paginación por cursor

Nunca offset. search devuelve {rows, next_cursor}; el cursor es opaco (base64 del último id). Las colecciones grandes no se degradan y una inserción concurrente no descoloca la página siguiente. Ningún endpoint devuelve una lista sin paginar.

Idempotency-Key obligatorio

En toda escritura. Misma clave + mismo request ⇒ se devuelve la respuesta guardada sin re-ejecutar. Misma clave + request distinto ⇒ IDEMPOTENCY_KEY_REUSED (409), nunca una sobrescritura silenciosa. Las respuestas se guardan 24 h en ir_idempotency, indexadas por hash canónico del request.

dry_run universal

?dry_run=true en cualquier escritura devuelve exactamente lo que devolvería la operación real más validations[] con lo que fallaría, y hace rollback del savepoint siempre. No escribe ni parcialmente, ni siquiera cuando todo era válido.

Errores con código estable

Los code son contrato público: se agregan, nunca se renombran ni se eliminan. Cada error trae retryable, requires_approval, docs_url y —cuando aplica— hint, model, record_id, field, trace_id.

Versión en la ruta

/api/v1, /meta/v1, /iam/v1. Cambios aditivos dentro de la versión; cualquier ruptura exige bump. La deprecación se anuncia con dos versiones de anticipación y headers Deprecation y Sunset. CI compara el OpenAPI contra una línea base y bloquea el merge ante una ruptura no declarada.

Lotes por defecto

El ORM es batch-first: la API de un registro es un lote de uno. Los campos calculados reciben la lista completa de registros afectados, nunca uno por uno: el N+1 es imposible por diseño, no por disciplina.

Definición de "terminado" para un endpoint

Tests unitarios y de integración pasando · cobertura ≥ 85 % de la lógica nueva · documentado en OpenAPI con ejemplos reales · campos con agent_hint y examples · errores con código estable registrado en el catálogo · dry_run soportado si escribe · idempotencia soportada si escribe · evento al outbox si cambia estado de negocio · entradas de ACL y record rules cuando aplique · sin regresión de SLO · registro en el changelog.

Convenciones declaradas en el plan, aún no implementadas

Estas forman parte del diseño de la v1 pero no están en el código todavía: ETag + If-Match en escrituras (hoy la concurrencia se controla con expected_version), parámetro expand= para traer relacionados en una llamada, headers RateLimit-* y rate limit por principal (viven en el gateway, que sigue siendo un esqueleto), y el envoltorio { "amount": "...", "currency": "..." } para importes de negocio (hoy los importes monetarios se serializan como string decimal simple, y el par moneda/valor solo aparece explícito en /iam/v1/authorize).

Modelo de seguridad #

Denegación por defecto en todas las capas. Sin grants no hay token de agente; sin ACL no hay operación; el claim cap nunca amplía lo que el usuario delegante puede hacer.

Delegación: token exchange con cadena act

Capability tokens

Un access token de agente lleva restricciones verificables sin consultar la base. El PDP evalúa cap antes de tocar el ORM.

Claim cap de un token de agente
{
  "iss": "https://iam.ordo.example",
  "sub": "agent:2d7c4b19-8e35-4a60-b1f7-9c0d2e3a5f64",
  "act": { "sub": "user:6f0f1e9c-7a41-4b8d-9c02-3e5a7b1d4c88" },
  "tenant": "acme",
  "cap": {
    "models": {
      "sale.order":   ["read", "create"],
      "account.move": ["read", "write"]
    },
    "limits": {
      "max_amount_per_op":  { "CLP": 5000000 },
      "max_amount_per_day": { "CLP": 20000000 },
      "record_domain": [["company_id", "in", [1, 3]]]
    },
    "requires_approval": ["account.move.action_post"],
    "deny": ["res.users.*"]
  },
  "exp": 1767225600,
  "jti": "..."
}
PiezaSemántica
modelsOperaciones permitidas por modelo. Un modelo ausente es CAP_NOT_GRANTED. Al fusionar varios grants: unión.
denyPatrones glob sobre modelo.operación o modelo.método. Se evalúa primero y siempre gana. Al fusionar: unión.
requires_approvalPatrones glob que fuerzan human-in-the-loop. Al fusionar: unión.
limitsMontos por operación y acumulado diario, por moneda. Al fusionar varios grants gana el más restrictivo.
record_domainDominio adicional aplicado a nivel de fila. Al fusionar: concatenación, es decir AND.
actCadena de delegación (RFC 8693). El usuario efectivo para el RBAC sale de aquí, no del sub.

Los acumulados diarios son el único punto con estado: viven en Redis como enteros en micros con TTL de 25 h. Si el contador está caído, el PDP deniega las operaciones con límite diario (CAP_LIMIT_BACKEND_DOWN): fail-closed, no fail-open.

Verificación de tokens

  • Solo RS256 y ES256. alg=none y algoritmos simétricos (confusión de clave con la pública) están cubiertos por tests de seguridad.
  • Claims obligatorios: iss, aud, exp, iat, sub, más tenant. Sin tenant, IAM_TOKEN_INVALID.
  • JWKS con caché de 300 s y refetch ante kid desconocido.
  • Los tokens de agente duran 900 s y llevan jti: la revocación se apoya en expiraciones cortas más el identificador del token.

Multi-tenancy: schema-per-tenant + RLS

Aislamiento de datos entre tenants: el riesgo de seguridad número uno del producto. Se defiende con dos barreras independientes, de modo que una fuga exija fallar las dos.

  1. Schema por tenant en PostgreSQL. El Environment fija SET LOCAL search_path al schema del tenant en cada transacción. El código de dominio nunca escribe el nombre del schema ni filtra por tenant: eso vive en una sola capa, y cualquier consulta que se salte el Environment se rechaza en revisión.
  2. Row Level Security como segunda barrera, con SET LOCAL ordo.tenant alimentando las políticas. Además de ocultar filas ajenas, la política impide escribirlas.
Detalle que hace la diferencia

RLS no se aplica a roles SUPERUSER ni con BYPASSRLS: conectarse con el rol dueño de las tablas deja la segunda barrera inerte. Por eso existe el rol ordo_app (NOSUPERUSER NOBYPASSRLS) y Environment.bind() ejecuta SET LOCAL ROLE ordo_app en cada transacción, incluso si el DSN trae credenciales privilegiadas. El binding se re-aplica tras cada commit: antes, un commit a mitad de request dejaba las consultas siguientes sin filtro.

Multi-company dentro del tenant es una dimensión distinta: company_id y allowed_company_ids en el contexto, resueltos por record rules.

Auditoría encadenada

Cada evento de autenticación, cada decisión del PDP y cada transición de aprobación se escribe en iam_audit_log, append-only, con encadenamiento por hash por tenant: hash = sha256(prev_hash + json_canónico(evento)). Se registran principal_id, la cadena act, el jti del token, el trace_id y la decisión de política. Los tests verifican que tanto la manipulación de un registro como su borrado rompen la cadena de forma detectable.
